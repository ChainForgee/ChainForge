# Merkle Allowlist Tool

Builds Merkle allowlist roots and proofs for the Soroban `aid_escrow`
contract's `claim_with_proof` verifier. **Zero dependencies** — Node's
`crypto` module only (no ethers, no merkletreejs, no keccak256).

## Canonical encoding (must match the contract exactly)

The contract verifies claims in `verify_merkle_proof_for_claimant`
(`app/onchain/contracts/aid_escrow/src/lib.rs`):

| Piece | Encoding |
|---|---|
| Leaf | `sha256(<canonical Address string>)` — the exact bytes `Address::to_string()` produces on-chain. The claim amount is **not** part of the leaf; the contract's verifier binds only the claimant address. |
| Pair combine | `sha256(left \|\| right)` with `left <= right` (byte-wise lexicographic comparison of the two 32-byte hashes). |
| Root | The Merkle root built from the leaves with that leaf and pairing rule, promoted unchanged for odd leaves. |
| Proof | Bottom-up list of sibling hashes, one per tree level, hex-encoded as **64 lowercase hex chars with no `0x` prefix**. |
| Metadata | `merkle_root` (64-hex root) and optional `merkle_root_expires_at` (unix seconds) set on a package's `metadata` map. |

Both the tool (JS) and the contract (Rust) implement this exact encoding. The
contract test suite pins the agreement: `tests/merkle_allowlist_tool.rs`
recomputes the root for `sample_allowlist.json` and asserts the contract's
`claim_with_proof` accepts the tool-format proofs on-chain (including a
hardcoded `EXPECTED_ROOT` generated by running this tool).

## Usage

```bash
cd tools/merkle-allowlist

# No npm install needed.
node index.js
```

Output is newline-delimited JSON. The first line is the root:

```
ROOT: <64 lowercase hex chars>
```

Then one JSON object per scenario (`valid`, `invalid_proof_path`,
`wrong_recipient`, `wrong_leaf`, `mismatched_root`), each with a stable
`result` object: `success: true` or `error: { code, message }`. A final
`proofs` object lists the per-address proof for every allowlist entry.

| Scenario | Expected `result` |
|---|---|
| `valid` | `success: true` |
| `invalid_proof_path` | `error.code: "INVALID_PROOF"` |
| `wrong_recipient` | `error.code: "WRONG_RECIPIENT"` |
| `wrong_leaf` | `error.code: "WRONG_LEAF"` |
| `mismatched_root` | `error.code: "MISMATCHED_ROOT"` |

## Publishing a root for a package

1. Replace `sample_allowlist.json` with the real allowlist (each entry:
   `{ "address": "<G.../C...>" }`).
2. Run `node index.js` and take the `ROOT:` value.
3. Create the package with metadata `merkle_root = <ROOT>` (and optionally
   `merkle_root_expires_at = <unix seconds>`).
4. Distribute each recipient's `proof` array (from the `proofs` output); they
   call `claim_with_proof(id, address, proof)`.

> Amounts are not bound by the contract's verifier. Binding per-recipient
> amounts into the leaf is a separate, open issue (the previous EVM-style
> `keccak256(abi.encodePacked(address, amount))` leaf is incompatible with the
> contract and has been removed).

## Previous EVM implementation

The old tool used `ethers` + `merkletreejs` + `keccak256` and produced
`keccak256(abi.encodePacked(address, amount))` leaves for an Ethereum-style
verifier that `aid_escrow` does not run. Every proof it generated failed
on-chain with `Error::InvalidProof` while printing "valid" locally — a
false-positive smoke signal. Those dependencies are removed; do not reintroduce
them without also changing the contract's verifier.
